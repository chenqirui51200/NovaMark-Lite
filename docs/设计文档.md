> 一个跑在浏览器里的 GPU **场景性能**评测工具（NovaMark-Lite）：
> 保留完整版 NovaMark 的三个「场景类」测试项 —— **球体环（原版最简场景）**、
> **毒蘑菇（Volume Shader BM）**、**综合测试（四段连续场景序列）**，
> 微基准测试不在本版范围内，
> 输出带维度分、逐段成绩表、帧时间分布、诊断结论和可分享成绩单的报告。

## 1. 项目定位

### 1.1 这是什么版本

本版是完整版 NovaMark 的**场景分支（Lite）**，目标非常明确：
**只测「场景负载下 GPU 实际能跑多少帧」**，并把这件事做扎实。

| | 完整版 NovaMark | 本版（Lite） |
|---|---|---|
| 测试项 | 15 项微基准 + 综合场景 + 毒蘑菇 + 原版球体环 | **球体环 + 毒蘑菇 + 综合测试**（共 3 项） |
| 维度 | 5 个（图形渲染 / 通用计算 / 显存与传输 / 交互延迟 / 综合场景） | **1 个**（综合场景，权重 100%，含 3 个子项） |
| 总分 | `20 × Σ(维度权重 × 维度分)` | `20 × 综合场景维度分`，维度分 = 三项加权几何平均 |
| 基线设备 | GTX 1060 6GB 级 → 1000 分 | GTX 1060 6GB 级（ring 365 / vsbm 176 / scene 147 FPS）→ 1000 分 |
| 理论达成率 | 有 | **无**（三项都是场景类负载，没有单一理论峰值可对应） |
| 稳定性压力测试 | 有 | 有（复用同一套场景，仅「完整 / 稳定性」预设启用，不进总分） |
| 评分曲线 / 等级 / 报告版式 / 版权 | — | 与完整版完全一致 |

不在本版范围内的微基准清单（这些 id 在本版中完全不存在）：
`fill`、`geometry`、`texture`、`shader`、`alu`、`fp32gemm`、`fp16`、`int`、
`bandwidth`、`upload`、`readback`、`latency`、`submit`。

### 1.2 为什么还要有一个「只有场景测试」的版本

1. **场景分才是玩家真正关心的数字。** 微基准回答「哪个单元弱」，场景类测试回答「能跑多少帧」；
   如果只想要后者，15 项微基准带来的额外 3–8 分钟测试时间是不必要的成本。
2. **微基准的跨平台可信度天然更差。** 它靠「自适应迭代数 + 墙钟计时」得到吞吐，
   在同步等不住 GPU 的设备上（典型是 iOS Safari 的 WebGL2）会系统性偏高；
   而本版三项的时长与帧数都由墙钟直接决定，不依赖迭代数校准，口径更稳。
3. **保留的这一组负载互补性很强**：球体环打「几何提交 + 填充」，毒蘑菇打「逐像素 ALU 与分支」，
   综合场景打「几何 + 着色 + 带宽 + 填充同时受压」。
   三者的分数高低常常不同步（例如弱核显在球体环上还能跑，在云海段直接掉到 40 FPS），
   因此几何平均后仍能反映真实体验下限。

### 1.3 竞品格局（为什么还要自己做）

| 方案 | 优点 | 对本版目标的缺口 |
|---|---|---|
| **3DMark** | 最权威，方法论成熟（缩放常数、97% 稳定性门槛、20 轮循环） | 需要安装客户端、依赖 DirectX、免费版功能受限 |
| **毒蘑菇 Volume Shader BM** | 打开网页就能吃满显卡 | 官方明确「没有综合分数」，只有 FPS，没有报告与指纹 |
| **Basemark Web 3.0** | 结构最产品化 | 商用需付费授权 |
| **MotionMark 1.3** | 方法论严谨 | 强依赖 rAF 与刷新率，测的是浏览器图形能力而非 GPU 吞吐 |
| **GFXBench** | 曾经的移动标杆 | 2025-11-30 已停服，浏览器版事实上已死 |
| **鲁大师** | 报告亲民 | 权重不透明且跨版本变更，历史成绩不可比 |

**结论：`浏览器内即开即用 + 一条有梯度的真实场景序列 + 归一化分数与完整报告 + 防伪指纹` 这个组合仍然是空位。**

### 1.4 设计原则

1. **绝不只给一个不透明数字**——维度分 + 总分 + 逐段成绩 + 帧时间分布。
2. **基线归一化**——饱和曲线把 FPS 映射到 0–100，基线设备恰好 50 分。
3. **固定负载、固定时长、丢弃预热**——同一项测试的内容在所有平台完全一致（只有时长按预设缩放）。
4. **稳定性独立成项**——不混进总分，单独给通过/未通过。
5. **报告帧时间分布而非仅平均 FPS**——1% low 与 P99 帧时间才是卡顿的真相。
6. **完整环境指纹**——GPU 渲染器串、后端、浏览器、OS、分辨率、DPR、刷新率、预设版本。
7. **物理合理性校验**——上下文丢失、API 校验错误、软件渲染一律作废或明确标注。
8. **分数带版本化**——基线一旦公布就不静默变更，改动要升级 `baselineVersion`。

## 2. 总体架构

### 2.1 技术选型：零构建静态站点

**纯 HTML + CSS + 经典脚本，没有任何 npm 依赖、没有构建步骤。**

- 评测工具的受众是「随手打开一个网页就想跑分」的人，多一步构建就少一半用户；
- 经典脚本（非 ES module）让 `file://` 双击打开也能工作（`type="module"` 在 `file://` 下会被 CORS 拦死）；
- 依赖第三方 3D 引擎会把分数绑死在引擎版本上——three.js 的 WebGPURenderer 就出现过性能回归，
  这会直接毁掉跨版本可比性。所以**计分内核与所有负载都是自持的**。

```

report.build()            → 报告 DOM + 图表
sha256(fingerprint)       → 成绩编号 NM-XXXX-XXXX + 结果指纹
```

## 3. 三项测试的负载设计

### 3.1 三项各打什么瓶颈

| # | 测试项 | id | 默认时长（标准预设） | 负载要点 | 主要压的单元 |
|---|---|---|---|---|---|
| 1 | 球体环（原版最简场景） | `ring` | 约 7 s | 约 288k 三角形 / 900 实例、单一几何 pass、无阴影无后处理 | 几何提交与图元装配、基础顶点/片元着色、填充 |
| 2 | 毒蘑菇（Volume Shader BM） | `vsbm` | 约 19 s（三档 5+6+8 s） | 逐像素沿视线步进 kernal 函数、符号变化检测、二分 + 黄金分割收敛、有限差分求法线 | 纯逐像素 ALU 与分支吞吐 |
| 3 | 综合测试（四段场景序列） | `scene` | 50 s | 星环 → 峡谷·黄昏 → 峡谷·云海 → 都市·风暴 | 几何 + 着色 + 带宽 + 填充同时受压 |

三项的分数高低常常不同步：球体环对几何提交与驱动开销敏感，毒蘑菇几乎不吃带宽，
而综合场景的云海段是极重的逐像素 + 带宽混合负载。因此几何平均能反映真实体验下限。

### 3.2 毒蘑菇为什么刻意降压

原版 `volumeshader.html` 是为「把显卡压满」设计的：`step = 0.01`、外层最多 200 步、
8 次二分 + 8 次黄金分割，命中后还要 6 次 kernal 求法线，**每像素约 220 次 kernal 求值**。
在手机上这会直接掉到个位数帧率，甚至触发浏览器杀页面。

本工具保持同一套算法与相机路径，只调三个旋钮（最大步数 / 步长 / 收敛次数）分三档递进：

| 档 | 最大步数 | 步长 | 二分 | 黄金分割 | 每像素求值 | 相对原版 |
|---|---|---|---|---|---|---|
| 低 | 110 | 0.020 | 6 | 5 | ≈ 99 | ≈ 45% |
| 中 | 150 | 0.014 | 7 | 6 | ≈ 142 | ≈ 65% |
| 高 | 190 | 0.011 | 8 | 7 | ≈ 186 | ≈ 85% |

三档共用同一套算法与相机路径，只有这三个旋钮不同，所以档内可跨设备对比。
三档光线总行程都约 5 个单位（与原版一致），保证打到的是同一层曲面细节。

预设通过 `levelScale` 缩放各档时长：快速 0.6、标准 1.0、完整 1.5。

## 4. 综合测试：四段连续场景序列

### 4.1 为什么要拆成多段

单一场景有两个问题：一是**负载上限受限于最轻的那个瓶颈**，二是**画面单调**，
无法覆盖真实 3A 场景里「几何 → 着色 → 参与介质 → 大规模实例」这几类差异极大的负载。
因此综合测试是一条**难度递增的连续序列**，每段独立计时、独立统计帧时间。

| 段 | 默认时长 | 名称 | 主要压的是什么 | 一帧 pass |
|---|---|---|---|---|
| 1 | 8000 ms | 星环（基础单场景） | 纯几何提交 + 基础着色（900 实例、无阴影/粒子/后处理） | 1 |
| 2 | 12000 ms | 峡谷·黄昏 | 阴影贴图（几何翻倍）+ PBR 五光源 + 3×3 PCF + 粒子 overdraw + bloom | 8 |
| 3 | 14000 ms | 峡谷·云海 | 在上一段之上加**参与介质**：40 步光线步进 × (2 次 5 阶 fbm + 4 次透光 fbm) | 9 |
| 4 | 16000 ms | 都市·风暴 | 换成城市几何（程序化窗格灯火、自发光边缘）+ 6 万粒子 + 低空沙尘 | 9 |

默认时长是「标准测试（standard）」预设的值。`segmentScale` 会按预设整体缩放
（快速 0.30、标准 1.0、完整 1.6），但**每段的相对比例与场景内容完全不变**。

### 4.2 一段序列内的 8 个 pass

| # | pass | 说明 |
|---|---|---|
| 1 | 阴影 | 从太阳方向正交投影，渲染地形 + 实例化岩石/楼体到 2048²（低档 1024²）深度图，正面剔除 |
| 2 | 背景 | 全屏程序化星云（5 阶 fbm）+ 星空 + 太阳光晕，写入 rgba16float HDR 目标 |
| 3 | 主体几何 | PBR（Cook-Torrance）+ 4 个轨道光源 + 3×3 PCF 阴影 + 程序化法线扰动 + 高度雾 |
| 4 | 粒子 | 2.4 万（都市段 6 万）实例化广告牌，加法混合、不写深度，制造大量 overdraw |
| 5 | 体积介质 | 全屏加法混合，40 步光线步进采样参与介质（仅云海段 0.52 / 都市段 0.24，其余段直接 return） |
| 6 | 亮度提取 | 半分辨率阈值提取 |
| 7 | 高斯模糊 H / V | 半分辨率两次可分离模糊 |
| 8 | 合成 | bloom + ACES 色调映射 + 暗角 + 色散 + 胶片颗粒，输出到画布 |

星环段只跑 2/3/8 三个 pass（无阴影、无粒子、无体积、无 bloom）。

### 4.3 场景内容全部程序化生成

不依赖任何外部资源，因此可以直接部署到任意静态托管：

- **地形**：`terrainSegments²` 网格（低 192² / 中 384² / 高 512²），CPU 侧 3 阶值噪声生成
  低频起伏 + 外圈岩壁抬升，顶点着色器再叠高频细节；
- **岩石**：icosphere（2 次细分，1280 三角形）实例化，逐实例用时间与序号做伪随机形状与朝向；
- **楼体**：24 顶点盒体实例化，近 2000 栋，高度/宽度/窗格灯火全部由哈希函数决定；
- **粒子**：程序化广告牌，位置/大小/颜色由哈希决定；
- **介质**：3D 值噪声 fbm 构成的云海与沙尘。

几何量（中档）：地形约 29 万三角形 + 1600 块岩石约 205 万三角形 ≈ **234 万三角形/帧**，
加上阴影 pass 翻倍。这正是场景分能反映真实 GPU 吞吐的原因。

### 4.4 计分方式

**场景分 = 整条序列的总帧数 ÷ 总时长**，也就是「整条序列的平均帧率」。
这样各段的权重自然等于其时长，不需要人为指定权重系数。

每段开始时先 `sync()` 一次清空队列，并丢弃该段前 900 ms 的帧（管线切换与着色器编译开销）；
末段还会丢弃尾部 600 ms。每段独立给出 `fps / frames / durationMs`，报告里以逐段条形表展示。

### 4.5 跨平台可比性

**所有档位使用完全相同的场景内容**，只有每段时长不同（`segmentScale`）。
这一点和微基准的处理相反 —— 微基准缩放的是「一次提交的迭代数」而保持单位不变，
场景缩放的只是**时长**，因为 FPS 是负载相关的量，内容一变就不可比。

用户选择的质量档（低/中/高）会改变几何量与粒子数，因此报告里会明确标注质量档；
跨设备比较请先确认**质量档与渲染分辨率一致**。

### 4.6 体积介质为什么贵

云海段每像素要做 40 次步进，每步 2 次 5 阶 fbm（每次 5 阶 × 4 次哈希 = 20 次哈希），
再加上被点亮时的 4 次透光 fbm。合计每像素约 **700 次哈希 + 少量超越函数**。
在 1280×720 上就是每帧约 6.5 亿次哈希运算 —— 这正是它把 1060 级显卡从 150 FPS 压到 40 FPS 的原因。
`resolution.z` 为 0 时整个 pass 直接 `return`，所以不需要它的段没有额外开销。

## 5. 测量方法论

本版的测量路径比完整版简单得多：**没有迭代数校准，没有多轮取中位数**，
只有「连续提交帧 + 等 GPU 真正完成 + 用 GPU 时间戳或墙钟算每帧耗时」。

### 5.0 全局预热：让结果不再依赖执行顺序

**问题**：`ring`（球体环）排在测试列表第一位，单帧只有 1–2 ms，是最轻也最敏感的负载。
页面刚加载完时 GPU 还在低频 / 低功耗状态，核心时钟尚未爬升到稳态，于是它**系统性偏低**：

| 测试项 | 实测 / 基线 | 3 次极差 |
|---|---|---|
| ring（排第 1） | 263 / 365 = **72%** | **22%** |
| vsbm（排第 2） | 155 / 176 = 88% | 4% |
| scene（排第 3） | 141 / 147 = 96% | 3.5% |

根因是**执行顺序**，不是负载本身：完整版 NovaMark 里 ring 排在 13 项微基准之后，
是被充分预热过的；本版它成了第一个重负载。

**为什么用「预热」而不是「调顺序」或「改基线」**：
基准测试的结果不该因执行顺序而变。调顺序只是把冷启动问题推给排在后面的另一个测试，
改基线则是拿标定值去迁就一个测量缺陷。正确做法是让所有测试都在同一稳态下起跑。

**做法**（`assets/js/bench/suite.js`）：

- 在正式测试列表**之前**跑一段全局预热，复用「球体环（中等档 900 实例）」的同一套编码器 ——
  与后面正式测的项目同构，因此预热到的是同一批着色器 / 管线 / 缓存状态；
- 时长常量：`WARMUP_MS = 5000`（标准 / 完整 / 稳定性预设）、
  `WARMUP_MS_QUICK = 2500`（快速预设整体只有约 41 s，按比例缩短）；
  现代 GPU 从空闲爬到稳态核心时钟通常在 1–2 秒量级，5 s 留足余量，
  相对标准预设约 85 s 的正式测量只占约 6%；
- **全程不创建结果对象、不参与评分**；任何异常都吞掉（预热失败不该让整轮测试跑不起来）；
- 计时从**预热之后**起算，因此报告里的「耗时」仍是正式测量的耗时；
- 通过 `onProgress` 发一条 `phase:'warmup'` 事件，界面显示「全局预热中」；
- 预热时长写进报告证书与文本报告，便于判断两次成绩的口径是否一致。

`BASELINE.ring` 保持 365 不变 —— 等内容确定后再一次性重标，而不是用基线去补测量缺陷。

### 5.0.1 ring 的方差：拉长测量窗口

预热把 ring 从 263 FPS 拉回 298 FPS（+13%，达基线 82%），**但三次极差仍有 18.6%**，
未达「5% 以内」的目标。根因是**负载特性**而不是预热不足：

| 测试项 | 单帧耗时 | 同样的帧时间抖动被放大 |
|---|---|---|
| ring | 1–2 ms | 最大（约为 scene 的 3 倍） |
| vsbm | 约 6 ms | 中 |
| scene | 约 7 ms | 最小 |

所以对 ring 采取**拉长统计窗口**（而不是继续加预热——边际收益递减，也不对症）：

```
RING_SECONDS = { quick: 8, standard: 15, full: 24 }
```

原实现是 `sceneSeconds × 0.14` 折算，标准预设只有约 7 s；现在标准 15 s（约 2 倍），
窗口变长后抖动被平均掉的比例更高。同时把 ring 的项内 `warmupMs` 从 800 提到 1500 ms。

**只加长窗口，不改负载本身**（实例数、几何、着色器一律不动），
因此 ring 的分数口径与其他项、与完整版仍然完全可比。

> 若极差最终仍降不到 5% 以内，则**接受现状并在文档注明**：
> ring 单帧仅 1–2 ms，方差天然大于 scene，这是负载特性。
> 不为追一个数字去改负载本身 —— 那会破坏跨版本可比性。

### 5.1 窗口批量提交 + 一次同步

早期版本逐帧提交、逐帧同步，结果是 GPU 在帧间跑空，而 GPU 时间戳跨了整个窗口，
把「等 CPU 编码下一帧」的空转也算了进去。现在改为：

1. 攒够 `pipelineDepth`（默认 2）个命令缓冲**一次性提交**；
2. 提交后调用 `ctx.sync()` 等 GPU 真正完成；
3. 有 `timestamp-query` 时读 GPU 时间戳，否则退化为墙钟；
4. 每帧耗时 = 窗口耗时 ÷ pipelineDepth。

因为不再逐帧提交，GPU 不会在帧间跑空，`pipelineDepth` 对结果几乎没有影响
（实测 821 vs 818 FPS），所以取 2 换取更细的采样粒度。

### 5.2 GPU 同步：本项目最大的坑

**WebGL2 里 `gl.fenceSync` 和 `gl.finish()` 都可能不等待 GPU。**

实测（Chrome 153 / Windows 11 / ANGLE D3D11 / NVIDIA P106-100）：
4096 次全屏混合只报 0.01 ms，200 次 1280×720 全屏填充只报 0.03 ms——物理上不可能。
用「加法混合计数」验证（n 层叠加后读回中心像素）：绘制**确实发生了**（n=64 → R=64，完全吻合），
但计时完全没有反映 GPU 时间。

**结论：唯一可靠的 WebGL2 同步手段是发起一次需要 GPU 回传数据的操作——读回 1 个像素。**

```js
gl.readPixels(0, 0, 1, 1, gl.RGBA, gl.UNSIGNED_BYTE, pixel);   // 真正的同步点
```

代价约 0.2–1 ms/次，相对于一整帧（数毫秒到数十毫秒）可以忽略。
（fence 等待仍然保留作为快路径，readPixels 作为兜底。）

WebGPU 侧同样不能只依赖 `queue.onSubmittedWorkDone()`——紧循环里连续提交时它会**提前 resolve**。
现在改用「GPU 侧围栏」：提交一个 4 字节的回读拷贝，然后等 `mapAsync`。

### 5.3 物理合理性校验（防错 + 防伪）

| 闸门 | 触发条件 | 处理 |
|---|---|---|
| 上下文丢失 | `webglcontextlost` / WebGPU `device.lost` | 该次成绩判为无效 |
| API 校验错误 | 测试前后 `ctx.errors` 新增条目 | 该次成绩判为无效并附首条错误 |
| 软件渲染 | SwiftShader / llvmpipe / Basic Render Driver | 明确警告「不代表真实 GPU 性能」 |
| WebGPU fallback adapter | `isFallbackAdapter = true` | 明确警告 |
| 样本过少 | 有效帧数 ≤ 40 | `valid = false`，不参与评分 |

WebGPU 里如果命令缓冲校验失败（例如绑定组不匹配），**整个命令缓冲会被拒绝、GPU 什么都不做，
但计时照跑**——所以第 2 条闸门是必需的。

### 5.4 其他防护

- **后台标签页**：监听 `visibilitychange`，切到后台即提示本次成绩可能偏低。
- **测量分辨率固定**：测试统一以固定像素数渲染（默认 1280×720），与窗口大小和 DPR 解耦。
- **计时精度如实标注**：记录 `crossOriginIsolated` 状态与实测 `performance.now()` 粒度；
  WebGL2 的 `EXT_disjoint_timer_query_webgl2` 在持续渲染循环里 `QUERY_RESULT_AVAILABLE`
  始终为 false（实测 24 深队列、3000+ 次读取全为空），因此综合测试在该后端只能退回墙钟。

## 6. 评分模型（单维度 / 三个子项）

### 6.1 单项分：饱和曲线

```
s = 100 × x / (x + x_base)
```

- `x` 为该项的实测平均帧率，`x_base` 为该后端对应的基线值（ring / vsbm / scene 各一个）；
- **基线设备每一项恰好 50 分**，分数天然落在 (0, 100)，不需要截断；
- 基线附近近似线性，远离基线后自然饱和，不会因为某块卡特别强就把总分撑爆。

（完整版里 `latency` 用倒数映射「越小越好」，本版没有这一类指标，因此只剩上面一条公式。
`score.partScore()` 的 `lowerIsBetter` 分支作为通用能力保留。）

### 6.2 维度分：三项加权几何平均

```
S = exp( Σ w_i · ln s_i / Σ w_i )        w_i = 1（三项等权）
  = (s_ring × s_vsbm × s_scene) ^ (1/3)
```

用几何平均而不是算术平均，是为了**让短板被充分暴露**：
两个 80 分加一个 0.7 分，算术平均是 53.6，几何平均只有 16.5 ——
这符合「跑分要反映真实体验下限」的直觉。

被跳过 / 失败 / 无效的子项不参与几何平均，权重在有效子项间重新归一化
（例如综合场景被跳过时，维度分 = ring 与 vsbm 两项的几何平均）。

### 6.3 总分

```
total = 20 × S
```

基线设备三项都在基线上（`s_i = 50`）→ `S = 50` → **总分恰好 1000**。

| 场景 | 三项子项分 | 维度分 S | 总分 |
|---|---|---|---|
| 三项都恰好等于基线 | 50 / 50 / 50 | 50 | **1000** |
| 三项都翻倍 | 66.7 / 66.7 / 66.7 | 66.7 | 1333 |
| 三项都减半 | 33.3 / 33.3 / 33.3 | 33.3 | 667 |
| 偏科：两项 80 分、一项 0.7 分 | 80 / 80 / 0.7 | 16.5 | 330 |

### 6.4 有效项与置信度

- `validParts / totalParts` 是「三项里几项有效」：`3 / 3`、`2 / 3`、`1 / 3` 或 `0 / 3`。
- 三项全部无效时 `total = null`，报告显示「总分不可用」并给出原因，而不是按 0 分惩罚。
  部分有效时仍能出分，但报告会把被跳过/失败的项标注出来。
- 置信度 = 有效项覆盖率（权重 0.75）+ 样本波动（权重 0.25），取值范围 0–1。
  覆盖率 = `validParts / 3`；样本波动取各项 CV 的均值（CV ≤ 2% 记满分，≥ 15% 记 0.3）。

### 6.5 等级划分

| 总分 | 等级 | 含义 |
|---|---|---|
| ≥ 2200 | S | 旗舰级 |
| ≥ 1500 | A | 高端 |
| ≥ 1000 | B | 主流 |
| ≥ 600 | C | 入门 |
| < 600 | D | 基础 |

等级表与完整版完全一致，因此**两个版本的总分在同一把尺子上**。

> ⚠️ 基线版本从 `1.2-scene-calibrated-1060` 升级到 `1.3-scene-ring-vsbm-calibrated-1060`：
> 维度由「只有 scene」改回「ring + vsbm + scene 三项几何平均」后，
> **同一个总分数字在两套刻度下含义不同，不要跨基线版本比较成绩**。

### 6.6 当前基线（v1.3-scene-ring-vsbm-calibrated-1060）

在一台 GTX 1060 6GB 级（NVIDIA P106-100）+ Chrome 153 + Windows 11 + WebGPU(D3D12) 的机器上实测标定：

| 后端 | 基线键 | 值 | 说明 |
|---|---|---|---|
| WebGPU | `BASELINE.ring` | **365 FPS** | 球体环最简场景（288k 三角形 / 900 实例 / 单几何 pass） |
| WebGPU | `BASELINE.vsbm` | **176 FPS** | 毒蘑菇三档整体平均（档位压力约为原版的 45%/65%/85%） |
| WebGPU | `BASELINE.scene` | **147 FPS** | 四段场景序列整体平均帧率 |
| WebGL2 | `BASELINE_BY_BACKEND.webgl2.ring` | **1865 FPS** | 墙钟口径系统性偏高（同一台机器） |
| WebGL2 | `BASELINE_BY_BACKEND.webgl2.vsbm` | **312 FPS** | 同上 |
| WebGL2 | `BASELINE_BY_BACKEND.webgl2.scene` | **422 FPS** | 同上 |

两套基线必须分开的原因见第 8.2 节。完整版里 `BASELINE` 的其余键（各微基准基线）
不在本版范围内；本版也不再有 `upload` / `readback` / `latency` / `submit` 等键。

**校准接口**（换机器/换后端整体偏移时使用）：

```js
Nova.score.setBaseline({ ring: 380, vsbm: 190, scene: 152, baselineVersion: '1.4-my-rig' });
```

### 6.7 绝对指数（不进总分）

`1000 × x / x_base`，1000 = 恰好等于该子项的基线，硬件爱好者用来横向对照。
本版不再计算**理论达成率** —— 它原本只对「有明确公开理论峰值」的微基准有意义；
三项都是场景类负载（球体环是最简几何提交、毒蘑菇是逐像素隐式曲面求交、
综合场景是几何 + 粒子 + 体积步进 + 后处理的混合体），没有单一峰值可对应。
`score.efficiency()` 作为同名同签名的空实现保留，避免上层出现分支。

5. **稳定性压力测试**（仅完整/稳定性预设）：稳定性百分比、通过判定、逐轮帧率曲线

**导出能力**：纯文本报告（可直接贴论坛，含逐段成绩与版权两行声明）、
JSON（完整数据，`copyright` 与 `copyrightNote` 字段强制保留）、
1200×700 成绩单长图（Canvas 手绘，页脚画入版权声明）、打印/另存为 PDF、

## 8. 跨后端与跨平台适配

### 8.1 目标：同档位可比，跨档位不崩

| 维度 | 做法 | 为什么 |
|---|---|---|
| 渲染分辨率 | **固定 1280×720**（与窗口尺寸、DPR 无关） | 体积云海、毒蘑菇与后处理都是逐像素负载，分辨率一变就不可比 |
| 场景负载 | **不缩放**，所有平台跑同一套内容（球体环 / 毒蘑菇三档 / 四段序列） | 这三项的指标都是 FPS，工作量一变 FPS 就不可比 |
| 每段时长 | 按预设缩放（`segmentScale` / `levelScale`） | 时长不影响负载强度，只影响统计样本量 |
| 缓冲区大小 | 按显存预算缩放（引擎保留该机制） | 纯粹的内存安全问题，与分数无关 |
| 质量档 | 显式标注在报告里 | 低/高档的几何量与粒子数不同，跨设备比较必须先对齐这一项 |

### 8.2 基线为什么必须分后端

参考机上同一套负载：**综合场景 WebGPU 147 FPS vs WebGL2 422 FPS（差 2.9 倍）**，
球体环 WebGPU 365 vs WebGL2 1865（差 5.1 倍）。
原因是**测量机制根本不同**，不是硬件差异：

| 后端 | 计时方式 | 测到的是什么 |
|---|---|---|
| WebGPU | GPU 时间戳查询（`timestamp-query`） | 纯 GPU 耗时 |
| WebGL2 | 墙钟 + `readPixels` 同步 | GPU 耗时 + CPU 提交开销，且同步在部分设备上等不住 GPU |

所以 `score/score.js` 同时维护 `BASELINE`（WebGPU 用）与 `BASELINE_BY_BACKEND.webgl2`（WebGL2 用），
**三个子项各有一个键**。结果对象带 `backend` 字段，评分时自动选用对应的一套。**跨后端分数不可比。**

### 8.3 设备档位画像

`Nova.detect.profileOf()` 依据 GPU 型号识别结果（优先用数据库里的权威类型，
识别不到才退回渲染器字符串与 WebGPU 架构名）产出：

| 档位 | 工作量系数 | 测试显存预算 | 典型设备 |
|---|---|---|---|
| 桌面独显 | 1.00 | 640 MB | RTX 3060 / RX 6600 / Arc A750 |
| 笔记本独显 | 0.65 | 448 MB | RTX 4060 Laptop |
| Apple 统一内存 | 0.50 | 320 MB | M1 / M2 / M3 / M4 系列 |
| 核显 | 0.30 | 224 MB | Iris Xe / UHD 630 / Radeon 780M |
| 移动 SoC | 0.18 | 160 MB | Adreno 740 / Mali-G715 / Maleoon 910 |
| 软件渲染 | 0.02 | 64 MB | SwiftShader / llvmpipe |

本版的场景负载**不按档位缩放工作量**（只缩时长：综合场景用 `segmentScale`、
毒蘑菇用 `levelScale`），因此档位系数只影响显存预算与引擎内部的缓冲区规模，不影响分数。

### 8.4 型号识别的三层兜底

1. **精确匹配**：`gpu-db.js` + 分片里的别名表（含 ANGLE 前缀、芯片代号、Laptop/Max-Q 变体）；
2. **改名卡/矿卡映射**：P106-100 → GTX 1060 6GB、CMP 30HX → GTX 1660 Super 等；
3. **档位兜底**：识别不到具体型号时按渲染器关键字 + 设备种类落到一个档位，
   用该档位的代表规格做参考机型对比，并在报告里标注「按档位估算」。

**通用串黑名单**：Safari 在 iOS 上只上报 `Apple GPU`，如果不屏蔽，
这个「什么都没说」的字符串会被反向包含判据命中任意带 `Apple GPU` 字样的别名
（实测会被误匹配成 M3 Ultra）。凡是 `apple gpu` / `generic renderer` /
`microsoft basic render driver` 这类通用串一律不参与型号匹配，直接走档位兜底。

## 9. 实现中踩到的坑（都已在代码中修复并注释）

| # | 坑 | 现象 | 修法 |
|---|---|---|---|
| 1 | WebGL2 fence/finish 不同步 | 4096 次全屏混合报 0.01 ms | 改用 1×1 `readPixels` 作为同步点 |
| 2 | WebGPU `onSubmittedWorkDone` 提前 resolve | 需要 ≥3.37ms 的工作量报 0.41ms | 改用「GPU 侧围栏」：4 字节回读 + `mapAsync` |
| 3 | 逐帧提交导致 GPU 跑空 | GPU 时间戳把「等 CPU 编码」也算进去 | 窗口内攒 `pipelineDepth` 帧一次性提交 |
| 4 | 帧数口径用错 | 用「采样数」当帧数，平均帧率被算成 1/depth | 用 `measuredFrames = 采样数 × depth` |
| 5 | 场景帧时间 CV 误报 | 实时负载逐帧抖动天然 CV 高 | 综合场景不参与 CV 告警，改看 1% low 与 P99 |
| 6 | 相机钻地 | 峡谷段相机低于地形高点，背面剔除后看穿地形 | 抬高相机轨迹下限并写进注释 |
| 7 | 阴影粉刺 | 深度图精度不足产生自阴影条纹 | 阴影 pass 正面剔除 + 3×3 PCF |
| 8 | 被跳过的测试返回 null | 评分阶段读 `r.id` 抛异常，整轮测试崩掉 | 跳过时返回结果对象而不是 null |
| 9 | 无头/虚拟环境 rAF 不触发 | 刷新率测量永远 pending，UI 卡在「测量中…」 | 加 3 秒超时兜底 |
| 10 | GPU 型号名清洗 | `ANGLE (NVIDIA, NVIDIA P106-100 (0x00001C07) Direct3D11 vs_5_0...)` 被截成半截 | 重写清洗规则，去 PCI ID / API 标记 / 括号尾巴 |
| 11 | 挖矿卡识别不到 | P106-100 不在消费级型号库里 | 加 rebrand 映射表（P104/P106/P102/CMP 系列） |

## 10. 已知局限

1. **只有一个维度、三个子项**：能看出「球体环 / 毒蘑菇 / 综合场景哪一项弱」，
   但无法进一步定位到填充率、纹理、带宽等具体单元。
   想知道后者，请使用完整版 NovaMark 的 15 项微基准。
2. **浏览器只能拿到「被包装过的」GPU**：同一块卡 Windows 走 D3D12、macOS 走 Metal、
   Linux 走 Vulkan，分数会有系统性差异。报告里记录了后端但无法消除差异。
3. **WebGL2 后端计时口径偏松**：`readPixels` 同步在部分设备上等不住 GPU，
   实测帧率会系统性偏高（参考机综合场景 2.9 倍、球体环 5.1 倍）。
   **两套后端的分数不应直接互相比较。**
4. **质量档与渲染分辨率会影响绝对分数**：跨设备比较必须同时对齐这两项；
   毒蘑菇的压力档由预设（快速 0.6 / 标准 1.0 / 完整 1.5）决定，也应保持一致。
5. **没有服务端**：因此没有在线排行榜，也无法做服务端重算与签名。
   浏览器端能可靠过滤「软件渲染 / 虚拟机 / 明显篡改」，但**对蓄意作弊给不出强证明**——
   所以输出表述是「可信度」与「可疑标记」，而不是「已验证」。

## 11. 后续路线图

- **服务端榜单**：GPU 型号 × 后端 × 设备类型 × 质量档分档排名。
- **逐 pass 计时**：WebGPU `timestamp-query` 在综合场景的 8 个 pass 上分别打点，
  报告里直接指出「阴影 pass 占比多少、体积云海占比多少」——这是单维度版本最有价值的下一步。
- **更多场景段**：延迟渲染 GBuffer、MSAA 1/2/4/8 对比、半分辨率 SSR、粒子物理。
- **毒蘑菇分档建模**：把三档各自单独出一个子项分，而不是只报三档平均值。
- **移动端适配**：移动端单独一套场景基线与质量档默认值。
- **分数分布对照**：与同型号、同后端、同质量档的中位数对比，给出偏离度。
- **校准向导**：用已知型号自动反算三项基线，一键生成团队内部基线文件。
