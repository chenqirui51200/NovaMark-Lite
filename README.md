> **这是 NovaMark 的 Lite 版：只保留「场景类」测试，共三项。**
> ① 球体环（原版最简场景）② 毒蘑菇（Volume Shader BM）③ 综合测试（四段场景序列），
> 三项全部归入唯一的「综合场景」维度（维度分 = 三项的加权几何平均）。
> 完整版 NovaMark 的 15 项微基准测试（填充率 / 几何 / 纹理 / 着色器 ALU / FP32·FP16 矩阵乘 /
> 整数原子 / 显存带宽 / 上传 / 回读 / 往返延迟 / 提交吞吐）**不在本版范围内**，评分维度由 5 个收敛为 1 个。
> 着色器、测试负载、报告、评分曲线与版权声明与完整版同源（后两项从完整版原样回归）。

一个完全跑在浏览器里的 GPU 场景性能评测工具：**球体环 + 毒蘑菇 + 四段连续综合场景**，
输出带维度分、逐段成绩表、帧时间分布、诊断结论和可分享成绩单的报告。

- **零构建、零依赖**：纯 HTML/CSS/JS，没有 npm、没有打包、没有第三方引擎
- **数据不出本机**：不上传任何东西，历史成绩存在浏览器 localStorage
- **双后端**：WebGPU 优先，自动回退 WebGL2（两个后端的基线分别标定）
- **跨平台**：Windows / macOS / Linux / Android / iOS / HarmonyOS，桌面独显到手机 SoC 全覆盖
- **参考规格库**：468 款 GPU（NVIDIA / AMD / Intel / Apple / 高通 / ARM / 华为 / 三星 / Imagination / 联发科）
- **三项测试，各打不同的瓶颈**：

  | # | 测试项 | 单位 | 负载要点 | 默认时长（标准预设） |
  |---|---|---|---|---|
  | 1 | 球体环（原版最简场景） | FPS | 约 288k 三角形 / 900 实例、单一几何 pass、无阴影无后处理 → 纯几何提交 + 基础着色 | 约 7 s |
  | 2 | 毒蘑菇（Volume Shader BM） | FPS | 逐像素隐式曲面光线求交（步进检测符号变化 + 二分/黄金分割收敛 + 有限差分法线），三档递进 → 纯逐像素 ALU 与分支 | 约 19 s（三档 5+6+8 s） |
  | 3 | 综合测试（四段场景序列） | FPS | 星环 → 峡谷·黄昏 → 峡谷·云海 → 都市·风暴，复杂度逐段递增 | 50 s |

- **综合测试 = 四段连续序列**（复杂度逐段递增，各段独立计时）：

  | 段 | 默认时长 | 内容 | 一帧的 pass |
  |---|---|---|---|
  | 1 星环 | 8000 ms | 最初的单一场景形态（单几何 pass、无阴影/粒子/后处理） | 1 |
  | 2 峡谷·黄昏 | 12000 ms | 384² 地形 + 1600 岩石 + 24k 粒子 + 阴影贴图 + PBR + bloom | 8 |
  | 3 峡谷·云海 | 14000 ms | 在几何之上再叠一层 40 步光线步进的参与介质（每像素约 700 次哈希） | 9 |
  | 4 都市·风暴 | 16000 ms | 换成近 2000 栋楼的城市几何（程序化窗格灯火）+ 6 万粒子 + 低空沙尘 | 9 |

  （时长是「标准测试」预设的值；快速 / 完整预设会按比例缩短或拉长，各段的相对比例不变。）

  综合场景分 = 整条序列的**平均帧率**（总帧数 ÷ 总时长），各段权重自然等于其时长。
- **浅色 / 深色主题**：默认浅色，右上角一键切换，选择会被记住
- **报告形态对标 3DMark**：维度分 + 总分 + 逐段成绩表 + 帧率曲线 + 成绩指纹

## GPU 参考规格库：扩充方式

规格库拆成多个分片并行维护，由一个聚合器合并（`assets/js/data/gpu-db.js` 末尾的 `mergeParts()`），
按 `id` 与**归一化型号名**双重去重：

| 分片 | 内容 |
|---|---|
| `gpu-db.js` | 主库字面量（基线机型与常见型号） |
| `gpu-db-part-nvidia-amd.js` | NVIDIA + AMD 桌面/移动/专业卡 |
| `gpu-db-part-intel-apple-qualcomm.js` | Intel 核显与 Arc、Apple 全系、高通 Adreno |
| `gpu-db-part-mobile.js` | ARM Mali/Immortalis、华为、三星 Xclipse、Imagination、联发科 |
| `gpu-db-part-techpowerup.js` | **由导入器生成**，可反复覆盖 |

### 从 TechPowerUp 批量导入

TechPowerUp 对自动化流量做了机器人验证，脚本抓不到；**用浏览器正常打开则不受影响**。流程：

1. 浏览器打开 <https://www.techpowerup.com/gpu-specs/>（建议翻页全部导出）
2. 全选表格内容复制，存成 `.tsv` / `.txt`；或直接「网页另存为」`.html`
3. 在 `工具区` 目录执行：

```powershell
node import-techpowerup.js 你的导出文件.tsv [更多文件...] [--dry] [--min-year 2008]
```

脚本会解析型号 / 核心 / 发布年份 / 接口 / 显存 / 频率 / 着色器数，换算 FP32 与带宽，
覆盖 `gpu-db-part-techpowerup.js`，并打印**厂商分布、类型分布与字段覆盖率**。

换算规则（全部写进每条记录的 `note` 里，可逐条审计）：

```
FP32 = 着色器数 × 2 FLOP × GPU 频率(MHz) ÷ 1e6      ← 两个前提缺一则 null
FP16 = FP32 × 2（打包口径）
带宽 = 显存等效速率 × 位宽(bit) ÷ 8                  ← 类型/频率/位宽不齐则 null
```

显存等效倍率按类型区分：GDDR7 / GDDR6X 为 PAM 编码（时钟 ×16），GDDR6 / GDDR5X ×8，
GDDR5 / GDDR4 ×4，GDDR3 与 HBM 系列 ×2，LPDDR / DDR 视作已给等效速率（×1）。

> **原则：读不到的字段一律写 `null`，绝不估算。**
> 自检时 `--dry` 可以只做解析与统计，不落盘。

## 快速开始

### 方式一：本地服务（推荐，功能完整）

需要 Node.js（任意 14+ 版本），不需要装任何依赖：

```powershell
node scripts/serve.js            # 默认 http://127.0.0.1:1234
node scripts/serve.js 9000       # 换端口
```

然后浏览器打开 <http://127.0.0.1:1234/>。

> 端口默认 **1234**：完整版 NovaMark 用 8765，两个项目可以同时起服务、互不干扰。

局域网里用手机测的话，服务默认监听所有网卡，用手机访问 `http://<电脑内网IP>:1234/` 即可。
注意：非 `localhost` 的 http 不是安全上下文，**WebGPU 会不可用**，但 WebGL2 后端照常跑；
想要手机上也能用 WebGPU，需要 https（可以套一层反向代理或自签证书）。

### 方式二：直接双击 `index.html`

`file://` 也能跑（脚本刻意写成经典脚本而非 ES module 就是为了这个），
但 localStorage、剪贴板、分享链接等能力可能被浏览器限制，建议还是用方式一。

### 方式三：部署到任意静态托管

整个目录就是站点根目录，直接扔到 GitHub Pages / Nginx / 对象存储即可。
WebGPU 需要安全上下文（https 或 localhost）。

## 使用说明

1. **硬件概览**：自动探测 GPU 型号、浏览器、系统与能力，给出测试清单预览。
2. **选配置**：
   - 测试预设：快速扫描（约 41 秒）/ 标准测试（约 2 分 35 秒）/ 完整测试（约 5 分 30 秒，含 20 轮稳定性）/
     稳定性压力测试（约 2 分钟，不出总分）。以上时长均已包含**全局预热**
   - **全局预热**：正式计分测试之前先跑一段中等负载（球体环中等档 900 实例），把 GPU 时钟/功耗拉到稳态。
     没有它时，排在第一位、单帧仅 1–2 ms 的球体环会因冷启动而系统性偏低（实测仅达基线 72%、三次极差 22%），
     而排在其后的毒蘑菇 88%、综合场景 96% —— 基准结果不该因执行顺序而变。
     预热带 5 秒（快速预设 2.5 秒），**不进结果、不计分**，时长会写进报告证书与文本报告。
   - **球体环的测量窗口已拉长到 15 秒**（快速 8 秒 / 完整 24 秒；原为约 7 秒）：
     它单帧仅 1–2 ms，是三项里对帧时间抖动最敏感的负载，窗口长一些才能把方差平均下来。
     只加长窗口，负载本身（实例数与几何）不变，分数口径仍与完整版可比。
   - 渲染后端：自动 / 强制 WebGL2
   - 渲染分辨率：1280×720（推荐，跨设备可比）/ 1600×900 / 1920×1080 / 2560×1440
   - 综合场景质量档：低（700 岩石 / 9k 粒子 / 192² 地形）/ 中（1600 / 24k / 384²）/ 高（3200 / 48k / 512²）
   - 毒蘑菇压力档由预设决定（快速 0.6 / 标准 1.0 / 完整 1.5 倍时长，档位步数不变）
3. **开始测试**：测试期间请保持标签页在前台、插上电源、关闭其他占用 GPU 的程序。
4. **查看报告**：总分、维度得分、三项评分明细、四段场景逐段成绩表、帧率曲线、诊断结论、硬件信息、成绩证书。
5. **导出**：文本报告 / JSON / 成绩单长图 / 打印为 PDF / 复制分享链接。

## 分数怎么读

- **总分**：基线设备（GTX 1060 6GB 级：球体环 365 / 毒蘑菇 176 / 综合场景 147 FPS）= **1000 分**。
  等级 S(≥2200) / A(≥1500) / B(≥1000) / C(≥600) / D(<600)。
- **维度分**：本版只有「综合场景」一个维度（权重 100%），含三个子项（球体环 / 毒蘑菇 / 综合测试），
  维度分是三项的**加权几何平均**，0–100，基线设备恰好 50 分。
- **总分的完整公式**：

  ```
  子项得分 s_i = 100 × x_i / (x_i + baseline_i)   x_i = 该项实测平均帧率，baseline_i = 该后端的对应基线
  维度得分 S   = exp( (ln s_ring + ln s_vsbm + ln s_scene) / 3 )   —— 三项等权几何平均
  总分         = 20 × S
  ```

  | 场景 | 三项子项分 | 维度分 S | 总分 |
  |---|---|---|---|
  | 三项都恰好等于基线 | 50 / 50 / 50 | 50 | **1000** |
  | 三项都翻倍 | 66.7 / 66.7 / 66.7 | 66.7 | 1333 |
  | 三项都减半 | 33.3 / 33.3 / 33.3 | 33.3 | 667 |
  | 偏科：两项 80 分、一项 0.7 分 | 80 / 80 / 0.7 | 16.5 | 330 |

  用几何平均而不是算术平均，是为了让短板被充分暴露（上表最后一行：算术平均给 1069，
  几何平均只给 330）—— 这符合「跑分要反映真实体验下限」的直觉。

- **绝对指数**：1000 = 恰好等于该子项的基线，硬件爱好者横向对照用。
- **有效项统计**：本版共 3 项，显示为 `3 / 3`；某项被跳过 / 失败 / 样本无效时是 `2 / 3` 或更低，
  该子项不参与几何平均、权重在有效子项间重新归一化；三项全部无效时总分为空。
- **稳定性**（仅「完整 / 稳定性」预设）：`最差一轮 FPS ÷ 最好一轮 FPS × 100%`，≥ 97% 为通过（对齐 3DMark 口径），**不进总分**。
- **理论达成率**：本版**没有**这一项 —— 它原本只对「有明确理论峰值」的微基准有意义，
  而本版三项都是场景类负载（球体环是最简几何提交、毒蘑菇是逐像素隐式曲面求交、
  综合场景是几何 + 粒子 + 体积步进 + 后处理的混合体），没有单一峰值可对应。

### 跨平台可比性怎么保证

| 做法 | 说明 |
|---|---|
| **固定渲染分辨率** | 默认统一 1280×720，与窗口大小、DPR 无关 |
| **负载内容一致** | 所有平台跑同一套内容（同样的球体环网格与实例数、同样的毒蘑菇三档算法与相机路径、同样的四段场景地形/岩石/粒子/pass 结构），不做按档位缩量 |
| **只缩时长不缩负载** | 综合场景用 `segmentScale`、毒蘑菇用 `levelScale` 缩放各段时长，负载强度不变 |
| **综合场景分按总帧数 ÷ 总时长** | 各段权重自然等于其时长，各平台口径完全一致 |
| **分后端基线** | WebGPU 与 WebGL2 的测量机制不同，三个子项各用各的基线（见下） |
| **质量档显式标注** | 用户选了低/高画质档时报告里会标注，跨设备比较请先确认质量档与渲染分辨率一致 |

某项被跳过或失败时，报告里会明确标注，权重自动重新归一化而不是按 0 分惩罚。

### 换机器后整体偏移怎么办

基线是在一台 GTX 1060 6GB 级机器上标定的，换后端（WebGL2）、换浏览器、换平台都可能整体偏移。
用已知型号反算一次，写入自己的三项基线即可：

```js
Nova.score.setBaseline({ ring: 380, vsbm: 190, scene: 152, baselineVersion: '1.4-my-rig' });
```

|---|---|---|---|---|

「快速扫描」预设会缩短它的三档时长。

## 跨设备测试（手机 / 平板 / 另一台电脑）

服务默认监听所有网卡，启动时会打印局域网地址：

```powershell
node scripts/serve.js            # 打印本机 + 局域网两个地址
node scripts/serve.js --local    # 只绑 127.0.0.1（更安全，别的设备访问不到）
```

### ⚠ 关键限制：局域网 HTTP 不是安全上下文

实测（Windows + Chrome 153）：

| 访问地址 | `isSecureContext` | `navigator.gpu` | 可用后端 |
|---|---|---|---|
| `http://127.0.0.1:1234` | **true** | **true** | WebGPU + WebGL2 |
| `http://192.168.1.2:1234` | **false** | **false** | **只有 WebGL2** |

`127.0.0.1` / `localhost` 属于规范里的「潜在可信来源」，而 **私有网段 IP 不是**。
WebGPU 只在安全上下文里暴露，所以在别的设备上用局域网 IP 打开时，
`navigator.gpu` 直接是 `undefined`，页面会自动回退到 WebGL2。

**想让手机上也能用 WebGPU，三选一：**

1. **Android + USB（推荐）**：`adb reverse tcp:1234 tcp:1234`，
   然后在手机上访问 `http://localhost:1234` —— localhost 是安全上下文，WebGPU 可用。
2. **HTTPS 隧道**：用 cloudflared / ngrok 之类把本地端口映射成 https 地址。
   iOS 只能走这条（没有 adb 等价物）。
3. **Android Chrome 临时放行**：`chrome://flags/#unsafely-treat-insecure-origin-as-secure`
   里加入 `http://192.168.1.2:1234`。能用但每台设备都要设一次。

### 跨后端对比的注意事项（重要）

| 后端 | 计时方式 | 可信度 |
|---|---|---|
| **WebGPU** | GPU 时间戳查询（`timestamp-query`，纳秒精度，窗口批量提交） | 高 —— 测的是 GPU 侧真实耗时 |
| **WebGL2** | 墙钟 + `readPixels` 同步 | 中 —— 同步在部分设备上等不住 GPU，实测值会系统性偏高 |

WebGL2 的 `EXT_disjoint_timer_query_webgl2` 虽然存在、调用也不报错，但在持续渲染的
循环里 `QUERY_RESULT_AVAILABLE` 始终为 false（实测 24 深队列、3000+ 次读取全为空），
所以三项测试都退回墙钟；而墙钟依赖 `readPixels` 真正等到 GPU。

参考机上同一套负载，两个后端差得很不一样：

| 测试项 | WebGPU | WebGL2 | 比值 |
|---|---|---|---|
| 球体环 | 365 FPS | 1865 FPS | 5.1× |
| 毒蘑菇（三档平均） | 176 FPS | 312 FPS | 1.8× |
| 综合场景 | 147 FPS | 422 FPS | 2.9× |

注意 WebGL2 那一列并不是「GPU 更强」，而是同步没等住 GPU 导致的系统性偏高；
球体环最简、单帧只有 1–2 ms，误差被放大得最厉害，所以比值最大。

**结论：只比同一后端的成绩。** 报告里会标出用的是哪个后端。

> **注意（本副本 2026-10-03 起）**：上表的「WebGPU = GPU 时间戳 / WebGL2 = 墙钟」只描述
> 参考机当年的实测环境。本副本的综合场景**两个后端已统一为墙钟口径**（等 `ctx.sync()`
> 确认 GPU 跑完后再取「上一窗口完成 → 本窗口完成」的间隔 ÷ 窗口帧数），因为 GPU 时间戳
> 不含每窗口同步往返期间 GPU 的空转，会让 HUD / 报告帧率虚高到实际产出帧率的近 2 倍。
> 实时 HUD、报告分段、最终结果三处现在同源，且与 `frames ÷ elapsed` 一致（实测 ±3%）。
> 详见文末「附：WebGL2 帧间隔比值不可作为卡顿判据」。

### 基线是分后端的

同一套负载，两个后端的实测口径差 1.8~5 倍，原因是**测量机制根本不同**，不是硬件差异：

| 后端 | 计时方式 | 测到的是什么 | 本版三项基线 |
|---|---|---|---|
| WebGPU | GPU 时间戳查询 | 纯 GPU 耗时 | `ring 365 / vsbm 176 / scene 147` FPS |
| WebGL2 | 墙钟 + `readPixels` 同步 | GPU 耗时 + CPU 提交开销，且同步在部分设备上等不住 GPU | `webgl2.ring 1865 / .vsbm 312 / .scene 422` FPS |

所以 `score/score.js` 里维护了两套基线：`BASELINE`（WebGPU 用）与 `BASELINE_BY_BACKEND.webgl2`（WebGL2 用），
**三个子项各有一个键**。结果对象带 `backend` 字段，评分时自动选用对应的一套。

**跨后端分数不可比**，只比同一后端的成绩。

#### 1.4 起：基线按「墙钟（含 sync）」口径重新标定（2026-10-03）

上表的 365 / 176 / 147 与 1865 / 312 / 422 是**旧口径**（综合场景优先用 GPU 时间戳）下的历史数字。
口径统一成墙钟后实测帧率整体下降（轻负载段最明显，接近一半），旧基线会把参考机量成 300 分左右。
因此两套基线都已重标，参考机（GTX 1060 6GB 级 / NVIDIA P106-100，Chrome / Windows 11）
在同一场次实测为：

| 后端 | ring | vsbm | scene | 参考机总分 |
|---|---|---|---|---|
| WebGPU | 573.78 | 228.23 | 151.37 | 1000（三项各 50 分） |
| WebGL2 | 123.73 | 120.27 | 145.78 | 1000（三项各 50 分） |

标定条件：ring 5s 窗口（1200ms 预热）、vsbm 三档各 2.5s、scene 四段 segmentScale 0.3（约 2.4/3.6/4.5/5.1s）。
基线版本号随口径升级为 `1.4-wallclock-ringfix-p106-20261003`；**1.3 及以前的成绩不能与 1.4 直接比**。
注意 WebGL2 的同步（围栏分片轮询 + 1 像素回读）比 WebGPU 的 `mapAsync` 贵得多，
同机同负载下 WebGL2 的实测帧率反而低于 WebGPU，这是**测量开销**而非硬件差异。

> 后缀 `-ringfix` 对应下面这条修复：WebGL2 综合场景**第一段（ring）**此前主体几何被驱动
> 整条丢弃，补齐后 ring 段的负载才是完整值，因此基线再重标了一版（实测六个数字相对上一版
> 变化都在 ±3% 内，属同批噪声范围）。

### 已知问题（已修）：WebGL2 综合场景第一段缺主体几何

**现象**：WebGL2 后端跑综合场景时，**只有第一段（星环，`mode:'ring'`）看不到几何**，
天空与地面正常、后面三段（峡谷/云海/都市）全部正常。原件 `webgpu-bench-scene` 同样存在此 bug，
与「合成翻转」等改动无关。

**根因**：`MAIN_FS` 里的 `shadowMap` 是 `sampler2DShadow`。ring 段 `shadow:false`，且它是整条
序列的第一段，所以 **texture unit 0 从未绑定过任何纹理（仍是默认纹理对象）**；ANGLE/D3D11 对
「比较采样器绑着不完整纹理」的 draw **直接丢弃且不报 GL 错误**。实测 `drawElementsInstanced
(count=960, instances=900)` 每帧都提交、参数合法、网格正常（icosphere(2) 972 顶点 / 960 索引），
但 HDR 目标里只有背景；把 `gl_Position` 换成铺满视口 + 把 FS 强制成品红，画面仍**逐字节不变**
（即一个片元都没被光栅化），同样补丁在 2/3/4 段立刻生效 —— 正对照证明了这一点。

**修法（`tests/scene.js` 的 WebGL2 分支，可直接移植到原件）**：准备一张 **1×1、深度值 1.0 的
深度纹理**（`DEPTH_COMPONENT24` + `Uint32Array([0xFFFFFFFF])`，NEAREST / CLAMP /
`COMPARE_REF_TO_TEXTURE` / `LEQUAL`，与 shadow map 同套采样状态），并把
`if (sc.useShadow) bindTex(0, shadow.tex);` 改成**无条件**的
`bindTex(0, sc.useShadow ? shadow.tex : whiteDepth);` —— unit 0 在任何段、任何时刻都有完整纹理，
阴影关闭时采样恒为「无遮挡」（`refZ ≤ 1.0` 恒真）。修复后第一段与 WebGPU 构图一致
（画布亮格 137 → 399），后三段无回归。

### 已知问题：iOS Safari 上的 WebGL2 计时

完整版在 iPhone 上用 WebGL2 后端实测时，微基准曾报出远超物理极限的数值
（A15 的 ALU 报成 15817 GFLOPS，理论约 1500）。根因是 WebGL2 的同步没等住 GPU，
校准环节据此把迭代数放大。本版不含微基准，**三项测试都不会出现这种放大**：
它们的时长与帧数由墙钟直接决定，不依赖迭代数校准；但仍然要记住
**iOS Safari 上 WebGL2 后端的帧率会系统性偏高（球体环最明显）**，请以 WebGPU 后端成绩为准。

## 附：WebGL2 帧间隔比值不可作为卡顿判据（2026-10-03）

`D:\AICode\webgpu-bench-scene-fix` 这一版做了两处与 WebGL2 相关的修正：

1. **画面倒置**：`shaders/scene-glsl.js` 的合成阶段去掉多余垂直翻转（WebGL 与 WebGPU 的 Y 轴原点约定相反，原来翻错了方向）。
2. **WebGL2 卡顿**：`tests/scene.js` 中 WebGL2 的 `pipelineDepth` 由 2 提到 8，并在每个窗口结束、以及重负载段逐帧让出主线程（`setTimeout 0`）。

### 为什么不要看 `p99 ÷ p50`

**headless 环境（无真实显示器）下这个比值会严重失真**：浏览器 rAF 在两次合成之间空转，`p50` 掉到约 3ms；而真实显示器上 `p50` 应为刷新周期（75Hz ≈ 13.3ms）。同一份代码，`p50` 变动 4 倍多，比值自然虚高。

**正确判据是绝对停顿值。** 修正前后的实测（WebGL2，8 秒段）：

| 指标 | 修正前 | 修正后 |
|---|---|---|
| 主线程长阻塞 | 每段多次 190~245 ms | **整轮 1 次 208 ms（段切换处）** |
| p99 绝对值 | — | **37.7 ms** |
| sync 分布 | — | **460 次中仅 1 次 > 100 ms** |
| WebGL2 吞吐 | 97 fps | **183 fps**（星环段 176 → 399，追平 WebGPU 431） |
| fps 口径 | — | **±3% 内**（星环 1.001、整体 1.008） |

### 结论

用户可感的卡顿已基本消除。**不再改动 `engine.js`** —— 要把那一次段切换的 208ms 也消掉，需要把 WebGL2 的 `sync()` 改成分片轮询围栏 + 让出的两阶段等待，而 `engine.js` 是主项目、精简版、毒蘑菇项目**共用**的核心文件，回归风险大于收益。

## 已知结构性问题：主库与分片存在重复 id（暂不处理）

GPU 参考规格库由**主库** `assets/js/data/gpu-db.js` 与**四个分片**（`gpu-db-part-*.js`）组成，启动时由 `mergeParts` 合并。

### 问题

两者之间存在 **71 个重复 id**，而 `mergeParts` 的规则是「**主库优先**」：

> 同一个 `id` 若同时出现在主库和分片里，**分片那一份会被静默丢弃**。

**这意味着**：如果你只改了分片里的某条数据，而主库里也有同 id 的条目，**你的改动不会生效，且不会有任何提示**。

### 添加/修改 GPU 数据时的正确做法

1. **优先改主库 `gpu-db.js`** —— 同 id 时被忽略的是**分片那一侧**，改主库必定生效
2. 若不确定某型号在哪一侧，**用校验脚本查**：
   ```
   node D:\AICode\工具区\gpu-db-check.js
   ```
   脚本会输出各文件条数、`mergeParts` 的新增/跳过统计，以及 11 条推导关系（填充率、带宽、FP32、FP16 规则等）的一致性检查结果。发现可疑项时以退出码 1 结束。
3. 改完**务必复跑脚本**，确认没有新增可疑项

### 另一处口径差异

分片里 Intel 的 `shaderUnits` 记的是 **EU 数**，主库记的是 **ALU 数**，靠 `mergeParts` 里的 `EU × 8` 换算弥合。**新增 Intel 条目前先确认你写的是哪一种**。

### 为什么暂不处理

统一到单一数据源（或给重复 id 加运行时告警）属于结构性改动，会牵动 `mergeParts` 的合并逻辑。当前已把**主库那一侧的错误值全部修正**，合并后的结果正确，因此**先记录、后处理**。

## GPU 规格库自检脚本

仓库内自带校验脚本，**Node 直接跑，不依赖浏览器与任何第三方包**：

```bash
node scripts/gpu-db-check.js
```

它会加载 `assets/js/data/` 下的全部分片与主库，输出：

- **各文件条数**与 `mergeParts` 的合并统计（新增 / 跳过重复 id / 按名合并）
- **分类统计**（按厂商、按类型）
- **11 条推导关系的一致性检查**（R1~R11）：
  - `fp32 = shaderUnits × 2 × 加速时钟`（**RDNA3/RDNA4 双发射为 ×4**，老 AMD VLIW 每 SIMD 16 SP）
  - `带宽 = 显存速率 × busWidth / 8`
  - `填充率 = ROP × 加速时钟`、`纹理率 = TMU × 加速时钟`
  - `FP16` 是否符合各厂商规则、`base ≤ boost`、`triangleRateGts` 必须为 null 等
- **可疑项清单**（含期望值与实际值）
- **跨文件重复 id / 同名规格冲突**

### 用法

```bash
node scripts/gpu-db-check.js              # 默认检查仓库内 assets/js/data
node scripts/gpu-db-check.js <目录>       # 指定其它数据目录
node scripts/gpu-db-check.js --json       # 输出 JSON 报告
node scripts/gpu-db-check.js --full       # 输出完整清单（不只摘要）
```

**发现可疑项时以退出码 1 结束**，可直接接入 CI 或提交前钩子。

> 注：运行后会在 `scripts/` 下生成 `gpu-db-check-report.json`（用 `--json` 时），属临时产物，不必提交。

**改数据后请务必跑一次** —— 本库历史上出现过「RDNA3/RDNA4 的 FP32 少算一半」「笔记本卡误用基准频率算填充率」「显存速率单位写成 Gbps 却按 MHz 换算」等错误，这个脚本就是为拦住它们写的。
